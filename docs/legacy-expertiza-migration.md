# Legacy Expertiza Data Migration

The project keeps the historical Expertiza data set available as
`anon_db/expertiza_anonymized_2026-10-20.sql` (~700 MB; 97 tables: the 85
legacy application tables, the 10 `goldberg_*` RBAC tables, and the two
Rails framework tables `schema_migrations` and `ar_internal_metadata`).
That dump uses the **old Expertiza schema** (tables such as `questions`,
`sign_up_topics`, `question_advices`, `teams_users`, a legacy
`schema_migrations` table, and legacy MySQL views like `score_views`).

Because the legacy tables already exist, the unguarded 2023-2025 migrations in
`db/migrate` **cannot** be run against it (`Table 'users' already exists`,
duplicate columns, etc.). The supported way to load the legacy data into the
development database is the repeatable procedure below, which:

1. **Resets the Docker MySQL/Redis volumes** and starts a clean stack
   (`db/init_databases.sql` recreates `reimplementation_development`).
2. **Imports the legacy dump** into `reimplementation_development` (the
   import strips the hardcoded `DEFINER` clauses from the legacy views — see
   caveats).
3. **Rewrites `schema_migrations`** (`db/legacy_surgery.sql`) so every
   2023-2025 migration — and the two legacy-colliding 2026 migrations
   (`20260227203258`, `20260313064334`, whose columns already exist in the
   legacy schema) — is treated as already applied.
4. **Runs `rake db:migrate`**, which executes the guarded 2026 bridge and
   convergence migrations (listed below).
5. **Verifies** table counts and key row counts.

## The 2026 migrations

**Bridge stage** (legacy names/shapes → canonical names/shapes):

- `20260101000000_prepare_legacy_expertiza_schema` — backfills the small
  pieces the 2026 chain expects (e.g. `duties.instructor_id`,
  `users.password_digest`, `signed_up_teams.project_topic_id`,
  `answers.item_id`).
- `20260209004302`, `20260209004501`, `20260320005757`, `20260320011304`,
  `20260810135129`, `20260813000001`, `20260925032901` — the guarded bridge
  chain: column renames, legacy table drops, `teams_users` →
  `teams_participants`, …
- `20261023000000_finish_legacy_expertiza_migration` — the final renames such
  as `questions` → `items` and `sign_up_topics` → `project_topics`,
  `users.fullname` → `users.name`; populates `items.question_type`; recreates
  `teams_users`; translates `duties`/`join_team_requests` data; aligns
  `review_grades`; rebuilds the `score_views` view.
- `20261023000001`, `20261024000001`, `20261024000002`, `20261025000001` —
  backfill missing reimplementation columns, normalize legacy column defaults,
  complete schema parity, and backfill missing timestamp columns.

All bridge migrations are fully guarded: they are no-ops on a database built
from the original 2023-2025 chain and safe to re-run.

**Convergence stage** (`20261101*`) — canonical shape parity:

- `20261101000001_signed_up_teams_nullable_fk` — makes
  `signed_up_teams.project_topic_id` / `team_id` nullable on the canonical
  chain (the legacy data contains `0` sentinels that the bridge converts to
  NULL).
- `20261101000002_convert_quiz_question_choices_to_utf8mb4` —
  `quiz_question_choices` was the last `latin1` table.
- `20261101000003_create_score_views` — recreates the `score_views` view
  against the canonical names (`ScoreView.questionnaire_data` depends on it).
- `20261101000004_widen_teams_comment_for_submission` — widens
  `teams.comment_for_submission` from the canonical 255-char `string` to
  `text` (legacy production comments reach 1,338 characters; no-op on the
  legacy source, whose column was already `MEDIUMTEXT`).
- `20261101000005_legacy_database_convergence` — the one-shot convergence
  (below).

## The convergence step (`20261101000005`)

The bridge makes the migrated database *naming-compatible*, but it is not
shape-identical to a database built from the clean 2023-2026 chain. A clean
database can never be "patched" into the legacy shape, so this migration
instead rewrites the legacy database to the canonical shape in a single step:

- **drops the ~26 legacy-only tables** the canonical chain never creates
  (`goldberg_*` RBAC tables, `sessions`, `versions`, `reviews`, `bids`,
  `courses_users`, `assignments_questionnaires`, other legacy review/meta
  tables, the `view1`/`view2` scratch views, …) — verified unused by every
  model and controller in the app;
- **widens legacy `INT` primary/FK keys to `BIGINT`** and aligns 100+ columns
  (types, nullability, defaults, `DATETIME` precision, boolean storage,
  `utf8mb4` collations) with `db/schema.rb`;
- aligns the index and foreign-key definitions with the canonical set.

The DDL payload lives in `db/legacy_convergence.sql`, generated by
`db/gen_convergence.py` (input: a post-bridge `mysqldump --no-data` of the
legacy database, compared against `db/schema.rb`). Regenerate it rather than
hand-editing.

Properties:

- **Guarded** — it detects a legacy source (the presence of legacy marker
  tables such as `sessions` / `goldberg_*`, or — for a partially converted
  database — the absence of the canonical-only `cakes` table) and is a
  **no-op on a canonical database**.
- **Irreversible by design** — `down` raises
  `ActiveRecord::IrreversibleMigration`; the safe path is to re-run the full
  procedure from the fresh anonymized dump. Individual FK drops are
  existence-guarded, so a partially completed convergence can be resumed by
  re-running `rake db:migrate`.
- **Schema-safe** — on a legacy source it suppresses the post-migration
  `db/schema.rb` dump, so the committed canonical `db/schema.rb` (version
  `2026_11_01_000005`) is never clobbered by a legacy-shaped dump.

**Expected end state:** the canonical 55 tables plus the framework
`schema_migrations` and `ar_internal_metadata` — 57 base tables in steady
state (a snapshot taken immediately after `rake db:migrate` shows 56, because
the bridge drops `ar_internal_metadata` and Rails recreates it on the next
connection) — and the single `score_views` view. "Canonical" means the
converged legacy shape the procedure produces, i.e. the committed
`db/schema.rb` (version `2026_11_01_000005`); the clean 2023-2026 chain
matches it except for cosmetic details (FK constraint names, DATETIME
precision) — see
[ADR-0001](adr/0001-canonical-schema-is-converged-legacy-shape.md).

## How to run

From the repository root:

- **Windows (PowerShell):**

  ```powershell
  powershell -NoProfile -ExecutionPolicy Bypass -File db\migrate_legacy_db.ps1
  ```

- **Linux / macOS (bash):**

  ```bash
  export MYSQL_ROOT_PASSWORD=expertiza   # both scripts fail fast if it is unset
  bash db/migrate_legacy_db.sh
  ```

> ⚠️ The procedure **deletes the current development database contents**
> (Docker volume reset) and replaces them with the legacy data. `rake db:seed`
> is intentionally skipped — the legacy data is the content of the development
> database.

### Manual steps (equivalent)

```bash
docker compose down -v
docker compose up -d
# wait for MySQL, then import (a few minutes):
# sed strips the hardcoded `DEFINER=`root`@`localhost` from the legacy views so
# they take on the importing user as definer instead (portable across environments)
docker run --rm --network reimplementation-back-end_default \
  -v "$(pwd)/anon_db/expertiza_anonymized_2026-10-20.sql":/dump:ro \
  mysql:8.0 sh -c "sed -e 's|/\*!50013 DEFINER=[^*]*\*/||' /dump | MYSQL_PWD=expertiza mysql -h db -uroot reimplementation_development"
# mark the old migrations as applied:
docker run --rm --network reimplementation-back-end_default \
  -v "$(pwd)/db/legacy_surgery.sql":/surgery:ro \
  mysql:8.0 sh -c "MYSQL_PWD=expertiza mysql -h db -uroot reimplementation_development < /surgery"
# run only the guarded migrations:
docker compose exec app sh -c "cd /app && RAILS_ENV=development bundle exec rake db:migrate"
```

## Verification

```bash
docker compose exec db mysql -uroot -pexpertiza reimplementation_development -e "
  SELECT COUNT(DISTINCT TABLE_NAME) AS tables
  FROM information_schema.tables
  WHERE table_schema = 'reimplementation_development' AND table_type = 'BASE TABLE';
  SELECT (SELECT COUNT(*) FROM users) AS users,
         (SELECT COUNT(*) FROM assignments) AS assignments,
         (SELECT COUNT(*) FROM answers) AS answers,
         (SELECT COUNT(*) FROM participants) AS participants,
         (SELECT COUNT(*) FROM items) AS items;
"
docker compose exec app sh -c "cd /app && bin/rails runner db/smoke_test_legacy.rb"
```

A full no-seed model smoke test is provided at `db/smoke_test_legacy.rb`
(loads ~25 core models against the migrated data and prints row counts).

Expected after a successful run: **57 base tables** in steady state (the
canonical 55 plus `schema_migrations` and `ar_internal_metadata`; a snapshot
taken immediately after `rake db:migrate` shows 56 until Rails recreates
`ar_internal_metadata`) and **1 MySQL view**
(`score_views`; the legacy `view1`/`view2` scratch views are dropped by the
convergence), the legacy row counts
(≈10,751 users, ≈955 assignments, ≈2,003,824 answers, ≈50,151 participants,
≈5,583 items, ≈4,757 project topics), `rake db:migrate:status` all `up`, and a
passing Rails smoke test.

## Notes and caveats

- **Legacy passwords are not valid** `bcrypt` digests (they are old
  `rest-authentication` SHA-1 values in `crypted_password`). The
  `password_digest` column exists (required by `has_secure_password`) but the
  legacy users cannot log in until their passwords are reset
  (`User#reset_password`).
- The dump's views carry a hardcoded `DEFINER=`root`@`localhost`, which breaks
  the import in environments where that account (or the
  `SUPER`/`SET_USER_ID` privilege) does not exist, so the import strips the
  `DEFINER` clause — without it, MySQL records the importing user as the
  definer (the views stay portable). Only `score_views` survives to the end:
  the `view1`/`view2` scratch views (no app usage) are dropped by the
  convergence, and `score_views` is rebuilt against the canonical table and
  column names.
- `teams_users` and `teams_participants` both exist in the end: the 2026
  bridge renames the legacy `teams_users` to `teams_participants`, and the
  final bridge migration recreates `teams_users` (populated from
  `teams_participants`) because the `Team` / `TeamsUser` models need it.
- **All remaining legacy-only tables are dropped by the convergence** (see
  above); none is referenced by the app. The bridge migration
  `20260320011304` already drops a curated subset (badges, sections,
  notifications, …) earlier in the run.
- Single-letter legacy statuses in `join_team_requests` are translated to the
  word values the app uses (`A`→`ACCEPTED`, `D`→`DECLINED`,
  `P`→`PENDING`); `invitations.reply_status` is left as-is because the app
  still uses the single-letter `W`/`A`/`D` values there.
- The legacy schema used `INT` primary keys; the convergence widens all
  primary/FK keys to `BIGINT`, so the migrated database is shape-identical to
  a canonical one (including join tables such as `assignments_duties`).
- **Pre-existing app limitation (not a migration defect):** legacy
  `questionnaires.type` / `items.type` STI values such as
  `ReviewQuestionnaire`, `SectionHeader`, `UploadFile` have no matching model
  class in the reimplementation (only e.g. `QuizQuestionnaire` is defined).
  Loading one of those rows through its STI class raises
  `ActiveRecord::SubclassNotFound`. The data is preserved as-is; support for
  those types is an application concern.
- `db/schema.rb` **stays canonical** after the procedure: the convergence
  suppresses the post-migration schema dump on a legacy source, so the
  committed `db/schema.rb` (version `2026_11_01_000005`) is never overwritten
  by a legacy-shaped dump. The development database itself holds the migrated
  legacy data.

## Production rollout

The production server runs **MariaDB 10.11** and the upgrade is performed
**in place** on the existing production database (no new instance, no
data copy). The canonical schema deliberately uses `utf8mb4_general_ci`
— a character set/collation pair both MySQL 8.x and MariaDB 10.x/11.x
support (the MySQL-only `utf8mb4_0900_ai_ci` is not used anywhere), so the
same migration chain works on either engine. The full chain has been
rehearsed end-to-end against a `mariadb:10.11` container, including the
MariaDB-specific foreign-key strictness (MariaDB refuses to re-define a
column that is part of a foreign key; the bridge/parity migrations drop
and restore constraints around every column rewrite).

### Run (in place)

`db/migrate_production_db.sh` in in-place mode performs the production
side end to end: preflight (server reachable, engine accepted) → schema
surgery (the `USE` line is rewritten to the existing database) →
`rake db:migrate` in the app image (`APP_IMAGE`; `APP_NET` for the
network) → verification → per-phase timing summary. In this mode nothing
is imported, nothing is dropped, and the database keeps its name:

```
IN_PLACE=1 TARGET_DB=<existing-db-name> MYSQL_HOST=<prod-host> MYSQL_PWD=... \
APP_IMAGE=<rails-app-image> APP_NET=<network> bash db/migrate_production_db.sh
```

(Without `IN_PLACE` the script keeps the fresh-target behavior: create a
new database, import a full dump, then convert it — useful for rehearsals
and as an alternative if the in-place decision changes.)

### Maintenance window and downtime

The in-place window is: stop app → rollback dump → surgery (seconds) →
`rake db:migrate` (the long phase) → smoke test → start app. Rehearsal on
a `mariadb:10.11` container with a full-scale copy of the production data
(anonymized dev dump, Docker on a developer laptop):

| phase | duration |
|-------|----------|
| surgery (`schema_migrations` rewrite) | ~0 s |
| migrations (guarded bridge + parity + convergence) | ~5 min |
| smoke test | ~1 min |

So the anticipated downtime is **~7–8 minutes** on laptop-class hardware
plus however long the final `mysqldump` takes at the start of the window
(production data volume; the dev-scale dump took ~1 minute). Measure both
on the production server during the rehearsal to get the real number.

### Cutover sequence

1. Freeze writes (stop the legacy app).
2. Take the rollback dump: a full `mysqldump` of the production database
   (data + structure) to safe storage. **This is the only rollback path**
   — the convergence migration is irreversible and cannot be undone in
   place.
3. Run the production script above (`IN_PLACE=1`).
4. The app's existing database user keeps its privileges on the unchanged
   database, so no new account is required; optionally create a new
   least-privilege account (`SELECT, INSERT, UPDATE, DELETE` — the app
   performs no DDL at runtime; the grants are printed by the script).
5. Start the reimplementation app against the same database and run the
   no-seed smoke test (`bin/rails runner db/smoke_test_legacy.rb`), then
   verify row counts.
6. Rollback if needed: stop the app and restore the step-2 dump over the
   database (the schema is fully restored with it).
